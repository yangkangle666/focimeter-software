# 焦度计项目团队统一开发规范（AI 必读版）

> **历史规划说明（2026-08-07）**：本文描述项目早期的三阶段总体规划，不能用来判断当前完成度。当前 M1、M2、M3 已合入 `develop`，当前“第一步/第二步”安排以仓库根 `README.md` 为准。文中的旧固定五点示例和旧分支流程不得覆盖正式接口、模块 README 或负责人最新决定。

> 使用方式：每个小组开始让 AI 写代码、改代码、整理资料前，先把本文件发给 AI，并要求 AI 确认遵守。  
> 目标：四个独立模块并行开发，互不影响进度，最后能快速合并成本地系统；后续再把本地系统优化封装成正式软件。

---

## 0. 给 AI 的开工指令

如果你是正在协助本项目开发的 AI，请先确认以下约束：

1. 本项目采用四个独立模块并行开发。
2. 每个模块必须可以本地独立运行、独立测试、独立交付。
3. 每个模块之间只能通过统一接口交换数据，不能私自依赖其他模块内部代码。
4. 第一阶段先做“本地系统模块成品”，不追求最终商业软件形态。
5. 第二阶段把四个模块按接口合并，集中修复 bug。
6. 第三阶段再优化创新，把本地系统逐步升级成正式软件。
7. 不允许硬编码绝对路径，例如 `D:\calibration.png` 这种路径只能用于临时测试，不能作为正式接口。
8. 所有输入、输出、错误、日志、单位、坐标系必须遵守本规范。

如果需求不清楚，先按本规范做最小可运行版本，不要擅自扩大范围。

## 1. 项目总目标

本项目要完成自动焦度计的软件/本地系统部分。

核心任务是：

```text
输入：标定图 + 测量图 + 配置参数
处理：识别光斑位置变化，完成标定、坐标转换和屈光参数计算
输出：球镜度 S、柱镜度 C、轴位 A、质量状态、日志和过程结果
```

第一阶段不是直接做完整软件，而是先做本地系统。

本地系统的意义是：

- 在本地电脑上跑通完整流程；
- 验证算法能不能正确工作；
- 让四个模块先各自独立完成；
- 为后续正式软件封装打基础。

---

## 2. 四个独立模块

项目固定划分为四个模块，每个模块由两人合作开发。

| 模块编号 | 模块名称 | 核心职责 | 第一阶段独立成品 |
|---|---|---|---|
| M1 | 输入与配置模块 | 管理图片、路径、参数、样本数据 | 能读取配置和图片，输出标准输入包 |
| M2 | 图像识别模块 | 处理图片，识别光斑，输出质心坐标 | 输入图片后输出标准光斑坐标 |
| M3 | 标定与计算模块 | 建坐标系，算位移，输出 S/C/A | 输入光斑坐标后输出镜片参数 |
| M4 | 本地系统与展示模块 | 串联流程，展示结果，日志和导出 | 能用模拟数据展示完整系统流程 |

每个模块必须做到：

- 独立运行；
- 独立测试；
- 独立输出结果；
- 可用模拟数据调试；
- 不等待其他模块完成。

## 3. 三个开发阶段

### 第一阶段：四个模块同时开工，做出模块成品

目标：每个模块都能独立运行，形成自己的小成品。

要求：

- M1 可以读取图片和配置，输出标准输入包；
- M2 可以读取图片，输出光斑坐标；
- M3 可以读取模拟光斑坐标，输出 S/C/A；
- M4 可以用模拟数据展示流程、结果、日志。

这一阶段允许使用模拟数据。

例如：

- M2 没有 M1 的真实输入时，可以自己读取样本图；
- M3 没有 M2 的真实坐标时，可以用 `mock_spots.json`；
- M4 没有算法模块时，可以用 `mock_result.json`。

第一阶段验收标准：

```text
每组必须交付：
1. 可运行模块
2. 使用说明
3. 输入样例
4. 输出样例
5. 错误样例
6. 当前问题清单
```

### 第二阶段：四个模块合并，修复 bug

目标：把四个模块接成完整本地系统。

推荐合并顺序：

```text
M1 输入与配置
  ↓
M2 图像识别
  ↓
M3 标定与计算
  ↓
M4 本地系统与展示
```

第二阶段重点：

- 不优先加新功能；
- 先让主流程跑通；
- 优先修接口问题；
- 优先修单位、坐标、字段不一致问题；
- 优先修无法复现的问题。

第二阶段验收标准：

```text
能在一台本地电脑上完成：
选择/读取标定图和测量图
读取配置参数
识别光斑
计算 S/C/A
显示或导出结果
保存日志
失败时给出错误原因
```

### 第三阶段：优化创新，本地系统升级成软件

目标：在完整本地系统基础上优化体验和可靠性。

可做方向：

- 图形界面；
- 参数保存和加载；
- 相机接入；
- 自动导入图片；
- 批量测试；
- 结果报告导出；
- 错误提示优化；
- 样本库管理；
- 测试报告自动生成；
- AI 辅助调参；
- 本地系统封装成安装包或可执行软件。

注意：第三阶段不能推翻前两阶段接口。优化创新必须建立在完整系统已跑通的基础上。

## 4. 统一接口是最高优先级

四个模块可以用不同方式实现，但接口必须统一。

接口包括：

- 输入文件格式；
- 输出文件格式；
- 字段名称；
- 单位；
- 坐标系；
- 错误码；
- 日志格式；
- 文件命名；
- 运行入口。

任何模块不能私自改接口。确实要改，必须通知其他三组，并更新本规范或接口说明。

## 6. 统一输入格式

系统主输入建议统一成一个 JSON 数据包。

示例：

```json
{
  "task_id": "sample_001",
  "calibration_image": "data/samples/calibration/calib_001.png",
  "measurement_image": "data/samples/measurement/meas_001.png",
  "config_path": "config/default_config.json",
  "run_mode": "local_image",
  "created_by": "module_test"
}
```

字段说明：

| 字段 | 含义 | 是否必须 |
|---|---|---|
| `task_id` | 本次任务编号 | 是 |
| `calibration_image` | 标定图路径 | 是 |
| `measurement_image` | 测量图路径 | 是 |
| `config_path` | 配置文件路径 | 是 |
| `run_mode` | 运行模式，例如本地图像或相机 | 是 |
| `created_by` | 来源，用于日志 | 否 |

路径规则：

- 优先使用相对路径；
- 不允许正式代码写死个人电脑绝对路径；
- Windows 路径要注意反斜杠转义；
- 文件不存在时必须返回错误，而不是程序直接崩溃。

配置参数统一放在 `config/default_config.json`。

示例：

```json
{
  "camera": {
    "pixel_size_um": 4.0,
    "image_width": 1920,
    "image_height": 1080
  },
  "optical": {
    "distance_m": 0.03,
    "hartmann_spacing_mm": null
  },
  "image_processing": {
    "roi_width_ratio": 0.9,
    "roi_height_ratio": 0.9,
    "median_kernel": 3,
    "tophat_kernel": 30,
    "otsu_a": 0.4,
    "otsu_b": 0.7,
    "max_depth": 2
  },

    "expected_spot_count": 5,

  },

    "pixel_threshold": 1.0,
```

## 8. 统一图像识别输出格式

M2 图像识别模块输出光斑坐标时，必须使用统一格式。

示例：

```json
{
  "task_id": "sample_001",
  "status": "ok",
  "image_type": "measurement",
  "coordinate_type": "image_pixel",
  "spots": [
    {
      "spot_id": 0,
      "role": "center",
      "x": 512.34,
      "y": 384.21,
      "confidence": 0.96
    },
    {
      "spot_id": 1,
      "role": "y_positive",
      "x": 512.10,
      "y": 284.88,
      "confidence": 0.94
    }
  ],
  "quality": {
    "expected_count": 5,
    "detected_count": 5,
    "is_usable": true
  },
  "error": null
}
```

要求：

- `spot_id = 0` 默认表示中心点；
- `role` 必须明确；
- 坐标单位默认是像素；
- `confidence` 范围为 `0.0` 到 `1.0`；
- 识别失败也要输出 JSON，不要只打印错误。

识别失败示例：

```json
{
  "task_id": "sample_001",
  "status": "error",
  "image_type": "measurement",
  "coordinate_type": "image_pixel",
  "spots": [],
  "quality": {
    "expected_count": 5,
    "detected_count": 3,
    "is_usable": false
  },
  "error": {
    "code": "SPOT_COUNT_MISMATCH",
    "message": "Expected 5 spots but detected 3."
  }
}
```

## 10. 统一错误格式

所有模块错误都必须使用统一格式。

```json
{
  "status": "error",
  "error": {
    "code": "ERROR_CODE",
    "message": "Human readable message.",
    "module": "image_recognition",
    "recoverable": true
  }
}
```

推荐错误码：

| 错误码 | 含义 |
|---|---|
| `IMAGE_NOT_FOUND` | 图片不存在 |
| `CONFIG_NOT_FOUND` | 配置文件不存在 |
| `CONFIG_INVALID` | 配置字段缺失或格式错误 |
| `IMAGE_LOAD_FAILED` | 图片读取失败 |
| `SPOT_COUNT_MISMATCH` | 光斑数量不符合预期 |
| `CENTROID_FAILED` | 质心计算失败 |
| `COORDINATE_SYSTEM_INVALID` | 坐标系建立失败 |
| `CALCULATION_FAILED` | 度数计算失败 |
| `UNIT_MISMATCH` | 单位不一致 |
| `UNKNOWN_ERROR` | 未知错误 |

## 11. 统一坐标系规则

坐标系是最容易出错的地方，必须统一。

### 图像坐标

```text
原点：图像左上角
X 轴：向右为正
Y 轴：向下为正
单位：pixel
```

### 标定坐标/测量坐标

```text
原点：标定图中心光斑
Y 轴：由中心点指向指定 y_positive 光斑
X 轴：由中心点指向指定 x_positive 光斑
单位：先保留 pixel，计算时再换算物理单位
```

### 统一要求

- 任何输出必须说明坐标类型；
- 不允许只给 `x, y` 而不说明坐标系；
- 计算模块必须明确图像坐标到标定坐标的转换过程；
- 角度统一使用 degree，除非字段明确写 `radian`。

---

## 12. 统一单位规则

单位必须写清楚。

| 物理量 | 统一单位 | 说明 |
|---|---|---|
| 图像坐标 | pixel | 图像识别默认输出 |
| 像元尺寸 | um | 配置中使用微米 |
| 物理长度 | m 或 mm | 字段名必须体现 |
| 屈光度 | D | S/C 输出单位 |
| 角度 | degree | A 输出单位 |
| 置信度 | 0 到 1 | 不用百分数 |

禁止：

- 一会儿用米，一会儿用毫米但字段名不变；
- 角度弧度混用；
- 把像素当成物理长度直接计算却不说明。

## 18. 合并方式

合并不是把四组代码硬拼在一起，而是通过统一接口接起来。

推荐合并方式：

```text
总控程序读取 input.json
  ↓
调用 M1，得到标准输入包
  ↓
调用 M2，得到标定图和测量图的光斑坐标
  ↓
调用 M3，得到 S/C/A 结果
  ↓
调用 M4，展示结果、保存日志、导出报告
```

合并前检查：

- 每个模块是否能独立运行；
- 每个模块是否能使用 mock 数据；
- 每个模块是否输出标准 JSON；
- 字段名是否一致；
- 单位是否一致；
- 错误格式是否一致；
- 日志是否能保存。

合并时不要做大改动。先加“适配层”解决小差异，等系统跑通后再统一重构。

负责人不需要每天检查每一行代码，重点检查：

1. 四个模块是否都在推进；
2. 有没有模块私自改接口；
3. 有没有模块依赖别人进度；
4. mock 数据是否齐全；
5. 输出字段是否统一；
6. 坐标和单位是否统一；
7. 合并风险是否提前暴露；
8. 每组是否留下运行说明和问题清单。

---

## 22. 最终统一口径

我们采用四模块并行开发方式：

```text
M1 输入与配置
M2 图像识别
M3 标定与计算
M4 本地系统与展示
```

第一阶段四个模块同时开工，每组做出可独立运行的模块成品。

第二阶段通过统一接口合并四个模块，集中修复 bug，形成完整本地系统。

第三阶段在本地系统基础上优化创新，逐步升级成正式软件。

核心原则：

```text
独立开发，统一接口；
本地跑通，再做软件；
先能合并，再谈优化。
```
