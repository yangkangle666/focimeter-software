# 焦度计项目 Git/GitHub 协作文档设计

## 目标

为依靠 AI 辅助开发的 8 人团队建立统一、可执行的 Git/GitHub 协作流程，使四个模块能够并行开发、组内互审，并在第二阶段稳定合并。

## 交付物

只生成以下两个正式文件，不生成 PDF 或其他重复版本：

1. `docs/governance/焦度计项目成员GitHub规范开发手册_人看版.docx`
2. `docs/governance/焦度计项目GitHub协作开发规范_AI必读版.md`

## 目标读者与用途

### 成员 Word 手册

- 读者：Git 和 GitHub 经验较少的团队成员。
- 用途：让成员能照着步骤完成首次加入、日常开发、提交、组内审核和问题处理。
- 文风：中文、通俗、步骤化；命令均提供可替换示例。

### AI Markdown 规范

- 读者：四组成员各自使用的编程 AI。
- 用途：在每次开发前约束 AI 的仓库操作、修改范围、验证、提交和交付行为。
- 文风：明确的 MUST、MUST NOT 和检查清单；不能依赖口头约定。

## 内容结构

### 成员 Word 手册

1. 仓库、六个长期分支和四组职责。
2. 成员需要提供的信息，以及接受仓库邀请的方法。
3. 首次安装、登录、克隆和身份配置。
4. 每次任务的标准流程：更新本组分支、建立个人 `task/...` 分支、让 AI 开发、验证、提交、推送、创建 Pull Request。
5. 两人小组的互审规则，以及项目负责人合并 `feature -> develop -> main` 的规则。
6. 统一接口、配置、模块目录和资料文件的修改权限。
7. 常见错误与恢复方法，包括分支切错、推送失败、文件冲突和 AI 改动越界。
8. 开工前、提交前和合并前检查表。

### AI Markdown 规范

1. 固定开场提问：成员、模块、阶段、任务、目标分支和现有输入材料。
2. 开工前仓库检查：工作区、当前分支、远程更新、规范文件和模块 README。
3. 权威来源优先级：接口契约、统一配置、模块 README、治理规范、任务说明。
4. 分支规则：从本组 `feature/...` 建立个人 `task/...`；禁止直接开发或推送 `main`、`develop` 和其他组分支。
5. 修改范围：默认只改本模块目录及本任务测试；共享文件必须先得到项目负责人批准。
6. AI 文件操作安全：保护用户已有改动、禁止强制推送和破坏性 Git 命令、禁止提交密钥和本机产物。
7. 实现与验证：使用统一 mock 数据，执行相关测试，检查 JSON 契约、相对路径、错误输出和日志。
8. 提交与 Pull Request：只暂存本任务文件，使用约定式提交，推送个人任务分支，PR 目标必须是本组 `feature/...`。
9. 冲突和异常处理：停止猜测、保留现场、报告具体文件和原因，不擅自重写历史。
10. AI 完成时的固定报告格式，以及可直接粘贴给 AI 的启动模板。

## 统一 Git/GitHub 流程

```text
接受邀请
  -> 克隆仓库
  -> 切换并更新本组 feature 分支
  -> 建立个人 task 分支
  -> AI 读取规范并确认边界
  -> 开发与本地验证
  -> 提交并推送 task 分支
  -> Pull Request 到本组 feature 分支
  -> 搭档审核
  -> 项目负责人合并 feature 到 develop
  -> 四模块联调通过后合并 develop 到 main
```

四个 `feature/...` 是模块长期分支；`task/...` 是个人短期任务分支。个人任务分支不会改变“四个独立模块”的项目结构。

## 权威来源与变更控制

1. `focimeter_system/docs/interface_contract_v1.md` 是接口唯一权威来源。
2. `focimeter_system/config/default_config.json` 是配置唯一权威来源。
3. 各模块目录中的 `README.md` 定义模块职责和本模块运行方式。
4. 新文档只引用以上文件，不复制一套接口字段或配置内容。
5. AI 和普通成员不得擅自修改统一接口、统一配置、模块边界、分支职责和共享目录。
6. 共享规则确需变更时，由项目负责人批准并先更新权威文件，再通知四组同步。

## 发布与分支同步

两份正式文档先在 `task/governance-github-docs` 完成和验证，再合并到 `develop`。随后在确认远程分支没有成员新提交的前提下，将同一文档提交同步到 `main` 和四个模块 `feature/...` 分支。若任何分支已经产生独立提交，则通过正常合并处理，不强制推送、不覆盖成员工作。

## 验收标准

- Word 文档能正常打开，标题、表格、代码块和分页清晰。
- Markdown 文件为 UTF-8，GitHub 和 AI 均可直接读取。
- 两份文档中的分支名称、模块名称、目录路径和合并方向完全一致。
- 不包含密码、Token、个人绝对路径或虚构的 GitHub 用户名。
- 不与现有接口契约、配置文件和团队总原则冲突。
- 新手成员可以仅凭 Word 手册完成一次标准任务流程。
- AI 可以仅凭 Markdown 规范判断允许修改的范围并给出合规交付。
